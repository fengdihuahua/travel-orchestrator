# 需求访谈协议（intake interview）

> **这是 S1 的执行手册。写任何行程之前，先把"你到底想怎么玩"问清楚。**
>
> 方法借自 grill-me 一类的"拷问式"需求澄清：**逐层往下挖，
> 能自己查到的事实绝不拿去问用户，共识没达成就不写方案。**
> v4.8.0 起节奏改为**一屏一层**：一屏里只问同一层的事（2-4 个子问题，各带选项），
> 用户一次答完一层，整场 4-5 屏结束。

先说清楚为什么不是"一次抛一整份问卷"，也不是"一条消息只问一个字"：

一次抛一串问题，用户只会挑最容易答的那两个答，剩下的留白，Agent 就按默认值补：
最后一版方案看着完整，其实是 Agent 自己的偏好披了用户的壳。真正该问的是**他自己没想清楚的地方**，
而那部分只有在追问里才会浮出来。反过来，把问题拆成十几条消息、一条问一个，
用户看到的是十几屏来回，中途就走了 —— 正确的位置在中间：**一层一屏，层内一次问全，层间顺序推进。**

---

## 0. 五条硬规则

1. **一屏一层。** 每屏只问**同一层**的 2-4 个相关子问题，每个子问题给 2-4 个具体、互斥的选项，
   等用户答完这一屏再进下一层。用宿主提供的选项问答能力出选项；宿主没有这种能力，
   就给带编号的选项列表让用户回一句。**同一屏里不要混层**（问 L1 的预算时别顺手问 L4 的忌讳），
   也**不要把无关问题堆进来凑数**：一屏 4 个问题已经是上限。
2. **每题带推荐项。** 把最可能的答案排在**第一位**并标「（推荐）」，选项描述里写清楚
   推荐的理由和代价。用户可以点，也可以自己写。
3. **能查的不要问。** 天气、日出时刻、潮汐、月相、门票价格、车次、开放时间：先查
   （`nature_forecast.py` / web 搜索），把查到的**事实嵌进问题里**再问。这是全篇最重要的一条：
   问用户"你想几点起床"是偷懒，问用户"干潮在 06:08，意味着 04:30 出门，接受吗"才是访谈。
4. **共识确认前不写方案。** 访谈结束输出一段「需求共识」，用户点头后才进 S2/S3。
   中途不要顺手给"参考行程"，那会让后面的追问全部失效：用户会开始评价你给的方案，
   而不是回答他想怎么玩。
5. **同一条追问最多追一层。** 用户答得含糊（"随便""都行""你看着办"）就是没答，要追一层；
   追一层还是含糊，**不要再绕**：直接给两个具体选项让用户挑（"A 蹲一个点拍日出 / B 换三个点走马观花"），
   或者按最可能的默认值定下来、写进「我替你定的」让他有机会否。

---

## 1. 五层决策树（4-5 屏走完）

按 L0 → L4 顺序推进。**每层的答案决定下一层问什么**，不要跳层，也不要在 L0 还没清楚时问装备。
屏的划分是默认节奏；用户已经自己说清的层直接跳过。

| 屏 | 层 | 要解决什么 | 问几个 | 答完能推出什么 |
|---|---|---|---|---|
| 1 | L0 意图 + L1a 日期 | 这趟为谁、为了什么；日期窗固定还是可挪 | 2-3 | 目的地候选、优先级取舍的裁判标准 |
| 2 | L1b 硬约束 | 人（**结构**）、钱（口径）、从哪出发、证件体力 | 2-4 | 行程骨架（几天、多快、住哪一带） |
| 3 | L2 口味 + L4 底线 | 节奏、早鸟还是夜猫、什么值得多花；安全底线、气象备选、忌讳 | 3-4 | 每天排几个点、几点起、钱花在哪、备选口径 |
| 4 | L3 自然观察专项 | 四项里哪几项真要玩、玩到什么程度 | **每项最多 2 问** | 专项时点、装备清单、替代方案 |
| 5 | 收尾 | 输出「需求共识」请用户确认 | — | 拍板，进 S2/S3 |

**收敛规则**：4-5 屏结束（快速通道 1 屏）。判断"问够了"的标准不是问满几屏，而是
**你能不能在不假设的前提下排出一张日程表**：排不出来，说明还缺哪层的答案，回去问那一层。

特殊情况：
- 用户说「你看着办 / 随便你安排」→ 走**快速通道**（只问第 1 屏），其余全部标
  `default_suggested` 写进 `request`，方案里明确列出"这几处是我替你定的，不合意可以改"。
- 用户赶时间（"十分钟给我个方案"）→ 先给**框架**（目的地/天数/预算档/节奏），
  标注"以下细节按默认值排，出发前用 S9 复核"，再回头补访谈。
- 用户上来就把 L1/L2 全说清了（"10/1 去威海 2 天，2 人 2500，想轻松点"）→
  **跳过已答的**，直接从没答的那层开始。别把已知信息再问一遍，那是仪式感不是访谈。

## L0 意图：这趟为谁、为了什么

先问这个，因为它决定后面所有取舍。同样去威海，庆祝结婚纪念日和带 5 岁娃放电，
是两个完全不同的方案。

问法（示例）：

> **这趟旅行主要是为了什么？**
> - 「放松 + 吃点好的，景点不重要」（推荐），那行程只排 1 个核心点，其余留给吃饭和发呆
> - 「陪家人/带娃，让小孩有得玩」，节奏要慢、有室内备选、避开长时间走路
> - 「拍照片，出片优先」，专项时点（日出/霞光/蓝调）优先于景点数量
> - 「难得请假，想一次看够」，可以接受早起 + 长车程，点位密度拉高

追问触发：用户说"就出去玩"→ 追一句「那这趟你最不想发生的是什么？」（堵车/赶时间/吃不惯/白跑一趟）
，负面清单往往比正面清单好排行程。

落盘：`request.why`（一句话）、`request.anti_goals[]`（不想要什么，可选）。

## L1 硬约束：时间、人、钱、证件、体力

**这一层的 4 个子问题放在一屏里问**（日期若在第一屏已经问过就不重复）。
顺序建议：同行人结构 → 预算口径 → 出发地 → 证件/体力。

**日期**：问清"固定窗"还是"可挪"（默认在第一屏和意图一起问）。
> 10/1-10/2 这个窗是定死的，还是能前后挪一天？（推荐：定死：那就不排任何依赖天气的孤注一掷项目，全部配雨天备选）

相对日期（"下个周末""国庆"）**必须转成绝对日期并让用户确认**，再往后所有计算都用绝对日期。

**同行人**：不是问人数，是问**结构**。""2 成人"和"2 成人 + 1 个 3 岁 + 1 位 70 岁"的行程完全是两件事。
> 同行里有需要特别照顾的吗？（学龄前小孩 / 老人 / 孕妇 / 伤病恢复期 / 都没有）
>：有的话，每天步行上限、有无厕所与避雨点、能不能爬台阶，都要跟着改。

**预算口径**：这是最常出错的字段，**必须问清是总额还是人均、含不含往返大交通**。
> 3000 是两人合计还是每人？包含往返交通吗？（推荐：两人合计且含交通：那扣掉 800 高铁后，当地只剩 2200）

**出发地**：默认从用户常驻地出发，但确认一句，因为影响首日可达性。
> 从北京出发对吧？那 10/1 早班高铁是 07:xx，到威海正好中午。

**硬约束**：证件（护照有效期、边防证）、体力上限（不能爬升超 300m）、忌口、晕车、必须带的东西。

落盘：`request.origin/dates/companions/budget/constraints[]`。

## L2 玩法口味：节奏、作息、钱花在哪

**节奏**（每天几个点）要在"体验深度"的语言里问，不要问"你一天想玩几个景点"，
用户对"几个点"没有感觉，但对"赶不赶"有感觉：

> 你希望的节奏是？
> - 「一天一个重点 + 周边，其余时间随便逛」（推荐）
> - 「多打卡几个地方，累点也行」
> - 「基本不排，睡到自然醒再看当天状态」

**作息**是关键分叉，直接决定日出/观星专项能不能排：
> 平时几点起、几点睡？出来玩愿意为日出早起吗？

**钱花在哪**：把预算拆成"住宿 / 吃 / 体验 / 交通"让用户排优先级，
比问"要住几星级"有效得多（很多人嘴上说随便住，其实愿意为吃多花钱）。

**住哪儿 · 吃什么**：这两件事占预算大头，而且**光靠预算问不出来**，必须单独确认一次。
一屏问完，每边给推荐项让用户挑（别让他填空）：

> 住和吃想怎么安排？（推荐：住得干净安静、吃走本地）
> - **住在哪一片**：景区门口（省通勤、贵） / 城区（便宜、要开车） / 车站附近（赶早班车方便）
> - **住宿底线**：能接受民宿吗？必须独立卫浴吗？停车、带娃/带老人有无要求
> - **吃什么**：本地特色为主 / 挑嘴要保险（有连锁） / 有忌口或必须吃到的某样

这里**只问偏好，不查库存**：本 skill 不接携程/美团这类要 Key 的接口，
问了也拿不到实时房价。落盘的是"住哪一片、什么类型、吃什么方向"，
价格与余房由页面上的平台入口交给用户自己看——方案不写死房价，写了就会过期。

落盘：`request.pace`（一句话）、`request.taste{rest,food,sightseeing,photo}`（1-5 权重，可选）、
`request.stay{area,type,max,notes}`（住哪一片 / 民宿还是酒店 / 能接受的价位档 / 硬要求）、
`request.dining{style,must_try,avoid}`（吃什么方向 / 必须吃到 / 忌口）。

## L3 自然观察专项：嵌进访谈里问

**这一步不是独立问卷，而是接在 L2 后面自然长出来的。** 做法分两段：

### 第一段：定"哪几项真的可行"，先查，再问

拿到 L0（意图）+ L1（日期地点）之后，**先跑一遍可行性核查**，再决定问什么。
不要问用户"你想观星吗"，要告诉他"你那个日期月亮 75% 亮、天顶亮到 21:30 才暗，
能看的是月面和亮星团，银河和深空基本没戏：还去吗，还是把观星换成看日出？"

| 专项 | 先查什么 | 查询方式 |
|---|---|---|
| 观鸟 | 该地该月有没有过境/越冬记录、低潮时刻与观鸟时段是否重合 | `nature_forecast.py bird --region ...` + `birdspot` |
| 观星 | 月相与月照、暗夜窗口、目标高度、目的地光污染等级 | `nature_forecast.py astro --lat --lng` |
| 日出日落 | 精确日出/日落、黄金/蓝调时刻、观景点朝向与车程 | `nature_forecast.py sun --lat --lng --date` |
| 赶海 | 干潮时刻与潮高、潮汐窗口、是半日潮还是全日潮 | `nature_forecast.py tide --city --date` |
| 朝晚霞 | 云量结构、能见度、湿度 → 霞光指数 | `nature_forecast.py glow --city --event` |

**取数一次取全，不要一项一项等。** `tide` / `astro` / `sun` / `glow` 四个子命令互相独立，
用户在屏 3 答完"想玩哪几项"之后，把要用到的专项数据**一条命令并行跑完**（shell 里用 `&` 串，
或一次调用把几个专项都取回来），别连着起四次进程让用户对着转圈。
只取用户表露过兴趣的项，不要预跑四项。

**核查结论分三档，问法跟着变**：

- **可做且条件好** → 直接问"要不要做、做到什么程度"
- **可做但条件一般**（月照强、潮位一般）→ **如实说清代价再问**："能看但打折扣，值得专门为它排早起吗？"
- **做不了**（那天没有潮汐窗口 / 目标在地平线下 / 不是流星雨季）→ **直说做不了，并给替代**
  （换项目 / 换日期 / 换地点）。不要为了"满足用户"硬排一个玩不到的项目：这是本 skill 的反幻觉底线。

### 第二段：逐项确认（每项最多 2 问）

**每项只问两件事**，其余从已答信息推默认值，写进「我替你定的」让用户有机会否：

1. **要不要玩、玩到什么程度**（可行性结论已经摆在问题里）
2. **那个真正改变排期的变量**（一般是"能不能凌晨起"或"要不要出片"）

下面每项列出的问题里，**只有前两条进访谈**，第三条起按默认值处理：

**观鸟**
1. 有具体想看的鸟，还是随便看看有什么？想看的鸟该季节在不在这里（先查，不在就换目标）
2. 能不能清晨 5:30 出门、在一个点蹲 2 小时？不能的话改傍晚次高峰
3. 〔默认〕装备：肉眼→推荐近滩点，双筒/长焦→推荐远滩点（默认按双筒排，共识里注明）
4. 〔默认〕要出鸟种照片 → 给"近距离可拍点"，不问也按"顺手能拍"排

**观星**
1. 主要想看什么：银河 / 流星雨 / 行星与月面 / 深空天体？
2. 能接受几点回、走多远？**去无信号暗点必须问**，并当场说明"结伴 + 告知同行人行程"
3. 〔默认〕没有赤道仪/广角/红光手电 → 写清"手机手持能拍到什么程度"
4. 〔**没有默认值**〕满月夜**不许默认"可接受"**：月亮照度 > 50% 的夜，必须在访谈里点明并让用户选
   （改看月面与地景 / 挪到月落之后的时段 / 干脆不排观星），选完写进方案并注明理由。
   不点明就等于拿"银河"骗了一次出行，红方 RT-L03 会拦。

**日出 / 日落**
1. 是看还是拍？拍的话机位朝向很关键（东向无遮挡 / 西向海平面）
2. 愿意为它 4:30 起、出门 40 分钟吗？不愿意 → 换成住处附近可步行到达的点
3. 〔默认〕云海是必须的 → 加"前一天降水 + 次日晨晴"触发条件，并明说成功率不保证
4. 〔默认〕火烧云是附加项 → 霞光指数纳入当日判断，写明是参考值不是官方预报

**赶海**
1. **能不能接受凌晨干潮？**：很多用户不知道干潮常在 04:00-07:00，这里必须给事实让他选：
   "干潮 06:08，窗口 04:38-07:38，要么 4:30 出门，要么放弃这次赶海，要么顺延到 D2 同一潮期"
2. 有没有小孩会走滩涂？有 → 时间上限收紧、必须写撤离时刻与潮沟警告
3. 〔默认〕带娃玩泥巴 vs 真要挖到东西：前者重安全与时间短，后者重滩涂类型与装备
4. 〔默认〕装备（雨靴/手套/铲/盐瓶）当地买 → 给采购点与价格

### 关系：专项之间会互相抢时间

L3 问完要**当场指出冲突**，让用户拍板（这也是访谈的价值）：

> D1 赶海 04:30 出门，D1 晚上还要不要排观星？两个连着来，中间只剩 6 小时含路上和洗漱。
> 我的建议是 D1 只看日落、观星放到 D2 晚（那天月相也更暗）。

落盘：`request.interests.must/prefer`（用户点名要的）+ `request.nature_caps{}`
（装备、经验、能接受的最早/最晚时间）+ 具体参数进 `itinerary.nature.*`。

## L4 风险与底线：把"出事的那个方向"先问出来

1. **安全底线**：带娃/老人/夜路/海边/高原，哪几条是绝对不能碰的？
   > 有没有"到了当地才知道不行就得撤"的情况？比如小孩走不动、老人爬不了台阶
2. **天气备选**：下雨怎么办：要备选方案，还是接受"下雨就回酒店"？
3. **不确定性容忍**：能接受"这个点可能去不成"吗？还是必须给确定的？
   （决定要不要排依赖天气的项目，以及方案里怎么标注）
4. **敏感点**：忌口、晕车、怕晒、不接受与人拼车、不接受民宿。

落盘：`request.risk{}`、`request.constraints[]`、`request.anti_goals[]`。

## 2. 追问对照表（本协议最该背下来的部分）

含糊答案不是答案。下面是常见含糊答案该怎么追：

| 用户说 | 别这么做 | 该这么追 |
|---|---|---|
| "随便玩玩" | 直接排 5 个景点 | 「随便是指一天 1 个点慢慢待，还是 3 个点打卡？」 |
| "都行，你安排" | 按自己偏好排 | 「那我说两个方案你挑：A 蹲一个点拍日出、B 换三个点走马观花」 |
| "想拍日出" | 直接排 4:30 起床 | 「机位单程 40 分钟，要 4:30 出门。接受吗？不接受我换住处附近的点」 |
| "预算 3000 够吗" | 按 3000 花钱 | 「3000 是两人合计还是每人？含往返交通吗？」 |
| "住哪都行" | 默认最便宜 | 「你更在意离景点近，还是住得舒服？这两个在威海差 200-400/晚」 |
| "想看点不一样的" | 排网红点 | 「不一样是指小众野点，还是别人没拍过的机位？」 |
| "可以早点起" | 直接排 5:00 | 「那 4:30 出门行不行？这是赶海窗口决定的，不是我想让你早起」 |
| "看情况吧" | 什么都不排 | 「那我按最坏情况排（下雨），另给一份晴天备选，你到时选」 |

**顶回去也是访谈的一部分。** 用户的决定里如果出现矛盾（预算与档期不符、带 3 岁娃
要凌晨赶海、满月夜要拍银河），不要默默照做也不要绕开，直接说清楚矛盾在哪、代价是什么，
再给替代选项让用户选。**照做出来的方案，最后是用户自己承担后果：这不算服务。**

---

## 3. 收尾：输出「需求共识」

访谈结束，用**固定格式**复述一遍，让用户确认。这是 grill-me 说的 shared understanding，
也是后面所有取舍的裁判标准。

```
## 需求共识

**这趟的主题**：<request.why>
**出发与目的地**：<origin> → <destination>（备选：…）
**时间**：<dates.start>–<dates.end>，共 N 天（固定 / 可挪 ±1 天）
**同行**：<companions>
**预算**：¥<amount>（总额 / 人均，含 / 不含大交通）
**节奏**：<pace>；每天大约 2–3 个点，<最早出门时间>–<最晚回>
**必须玩到**：<interests.must>
**能做则做**：<interests.prefer>
**不想要的**：<anti_goals>
**硬约束**：<constraints>
**自然观察**：
  - 🐦 观鸟 — <目标鸟种/时段/装备>；<可行性结论>
  - 🌙 观星 — <目标/能接受的最晚时间/地点>；<可行性结论>
  - 🌅 日出 — <哪个点/是否拍摄>；<可行性结论>
  - 🦀 赶海 — <窗口/带不带娃>；<可行性结论>
**我替你定的**（默认值，可改）：<default_suggested 的项>
**还没定的**（要你现在定，或我去查）：<unknown 的项>

以上对吗？有要改的直接说，改完我就开始排。
```

用户确认后：
1. 把这段落盘：`request.*` 写结构化字段，**每个被问到的决定在 `decisions[]` 里留一条**
   （`question` / `choice` / `reason`；被顶回过、用户仍坚持的加 `pushed_back` 说明）
2. 进入 S2/S3。**S3 调研时如果发现与共识冲突的事实**（门票预约不上、日期撞上封海），
   回头找用户改共识，不要自己偷偷改方案。

**落盘口径（重要）**：`decisions[]` 是**生成过程记录**，和红方复核一样
**不渲染进交付物**：读者要的是行程，不是问答流水。访谈的价值体现在方案本身：
时点排得对、取舍有道理、被顶回过的风险改写进「踩坑指南」。

交付物里只保留共识的**结论**：

| 落盘字段 | 进不进交付物 | 进的话显示在哪 |
|---|---|---|
| `decisions[]`（问答流水） | ❌ 不进 |，（S10 改方案时可回看，用来判断改动会碰到谁） |
| `request.why` | ✅ 进 | 「一页速览 → 这趟的主题」 |
| `request.constraints[]` | ✅ 进 | 「一页速览 → 硬约束」 |
| `request.*` 其余（日期/同行/预算/节奏/专项） | ✅ 进 | 「一页速览」各格 |
| `request.nature_caps`（装备/经验/作息） | ❌ 不进（并入专项建议与待办清单） |：|

## 4. 反例清单（这些做法会让访谈失效）

- ❌ 一屏里问超过 4 个问题，或把不同层的问题混在一屏（用户只会答最省事的两个）
- ❌ 把一条能问完的一层拆成五六屏来回问（用户中途就走了：整场 4-5 屏是上限）
- ❌ 选项写成"是 / 否"、"好 / 不好"，除非问题真的是二元的
- ❌ 问用户能自己查的事实（天气、票价、车次、日出时刻）
- ❌ 用户还没答完就先给一版方案（后面所有回答都会被"方案已经在了"锚定）
- ❌ 把"随便""都行"当作答案收下，或者在同一条含糊答案上来回追三层
- ❌ 发现矛盾却照做（不加说明地排一个玩不到的项目）
- ❌ 为了显得专业，把已知信息再问一遍
- ❌ 第 6 屏还在问细节（该收敛了：能不能排出一张表就是标准）
