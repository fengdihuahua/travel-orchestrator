# 红方评审清单

红方不是"再检查一遍"，是**站在出事故的那一边想问题**。

蓝方（主规划）写的是"这样玩挺好"，红方问的是"这样玩哪里会崩"。
两者的立场天然对立，这样才能把方案里自我感觉良好的部分逼出来。

---

## 一、红方的三条纪律

1. **不许说"基本没问题"。** 挑不出问题就明确写"本轮无发现"，不许用模糊话糊弄。
2. **每个质疑必须落到具体一行。** 不能只说"行程太赶"，要说"D2 从 15:00 返程倒推，
   环海路骑行实际只剩 2 小时 40 分，扣掉往返交通剩不到 2 小时"。
3. **质疑要给替代动作。** 指出问题不给解法等于甩锅，方案作者没法执行。

---

## 二、严重度定义

| 级别 | 判定标准 | 处理 |
|---|---|---|
| `blocking` | 会导致人身危险、行程物理上跑不通、或事实错误到会让人白跑一趟 | 必须改完才能交付 |
| `major` | 显著影响体验或明显超支，用户照做会不满意 | 应改；不改要写进"已知取舍" |
| `minor` | 打磨项，不影响能否出行 | 可留待版本迭代 |
| `info` | 记录用，比如某个数据没查到、某条依据偏弱 | 只需标注 |

**安全相关一律升为 `blocking`。** 判断标准很简单：这件事出错的后果，
是"玩得不爽"还是"人回不来"。

## 三、六轮质疑

### 第 1 轮：时间能不能真跑通

逐个槽位问：

- 上一项结束到下一项开始，够不够走完这段路？（含排队、找路、停车）
- 时间窗有没有重叠？（重叠就是有一项注定做不到）
- 跨零点了吗？跨零点的写法（如 `23:00-24:30`）本身是无效的，要么拆成两项，要么写 `23:00-00:30` 并标注跨日
- 这一天加起来，用户是在旅游还是在赶场？带娃带老人时尤其要重算
- 凌晨和清晨连着排了吗？观星到 23:30、次日 05:00 起拍日出，中间只剩 5.5 小时，
  还要扣掉回酒店和洗漱，这种排法第一次出行的人会崩

### 第 2 轮：地理上说得通吗

- 同一天是否在同一片区？东一头西一头就是路线折返
- 地图上的直线距离和实际车程差多少？沿海公路、盘山路、跨海大桥都会拉长时间
- 观星点、日出点、赶海点这些"特殊时点"的地方，回程怎么办？夜里有没有车？
- 有没有"看着近其实过不去"的情况（无桥、禁行、涨潮淹没的堤道）

### 第 3 轮：钱够不够

- 分项上限加起来，超没超用户给的预算？（最常见的就是默认超支）
- 大交通是不是按真实票价填的？节假日票价和提前购票折扣差很多
- 门票是否漏了区间车、索道、停车费、保险？
- 儿童和老人的优惠票单独算了吗？**别用成人价乘人数了事**
- 有没有留弹性余量？没有余量的预算是纸面上的

### 第 4 轮：安全（这一轮决定 blocking）

- **赶海的推荐窗口盖住干潮时刻了吗？** 窗口终点越过干潮后约 1.5 小时，滩涂就开始回水
- 涨潮前撤离的时间留够了吗？涨潮速度远快于步行速度，滩涂深处更危险
- 有暗沟、礁石浪花带、离岸流提示吗？带孩子的话看管要求写了吗？
- 大风、台风、雷雨天的取消条件写了吗？几级风禁赶海？
- 观星点夜里有没有信号和照明？结伴要求、保暖、红光手电提了吗？
- 高海拔观星的缺氧、低温、夜间行车风险提了吗？
- 日出点在悬崖/水边，有没有护栏、湿滑、拥挤踩踏的风险？

### 第 5 轮：事实有没有出处

- 每条数字（时刻、票价、里程、时长）能追到来源吗？
- 来源的日期是哪天？**潮汐、日出、月相、天气这四类一天一变，来源超过 30 天就是废数据**
- 查不到就写 `unknown`，不要用 0 或"约"来填空
- 有没有把"模型估算"当成官方数据？（如自建霞光评分，必须标"非官方预报"）
- 来源之间有没有互相矛盾？矛盾时选权威的并说明

### 第 6 轮：用户体感（最后一轮，也最容易被跳过）

- 这个节奏，用户本人受得了吗？还是只适合体力好的人？
- 同行人里有小孩/老人/孕妇吗？他们的节奏和成年人不一样
- 有没有一个"什么都不干"的缓冲段？全程满档的方案往往第一天就崩
- 吃饭时间是不是被景点挤掉了？海鲜市场代加工要排队多久？
- 用户明确说"想看的"那件事，是不是真的排进去了？

## 四、高频陷阱速查

这些是旅行方案里反复出现的错误，红方每轮都该扫一遍。

| 陷阱 | 为什么危险 | 怎么查 |
|---|---|---|
| 潮汐窗口算错 | 真的会出人命 | 窗口必须盖住干潮，终点不超干潮 + 1.5h |
| 用远期的潮汐数据 | 数据约 10 天有效，之后返回 null | 看 `data_valid_until` 和 `partial` 标记 |
| 日出时刻和活动窗对不上 | 跑到地方太阳已经升完了 | 活动窗要含日出前后各 1 小时 |
| 满月夜安排观星 | 银河基本不可见，白跑 | 月亮照度 > 50% 就该改目标 |
| 保护区当景点写 | 禁入区进去要担责 | 查保护区开放范围与许可要求 |
| 节假日按平日估算 | 门票、车次、车位全不一样 | 明确标注"节假日价"并加排队余量 |
| 预算用成人价乘人数 | 儿童票往往半价或免票 | 逐人核算优惠票 |
| 天气只写平均值 | 掩盖了极端天气 | 逐日预报 + 极端天气备选 |
| 备选方案没触发条件 | 用户不知道什么时候该用它 | 每条备选写清触发条件与接回点 |
| 把估算写成确定 | 用户以为已确认 | 标注 estimated 并给出误差范围 |

## 五、输出格式

红方结论写回 `red_team` 字段（落在 `parts/*_red_team.json` 分片），供渲染器呈现、供下一轮比对：

```json
"red_team": {
  "reviewer": "red-team",
  "rounds": [
    {
      "round": 1,
      "scope": "时间/地理/成本/安全/事实/体感",
      "findings": [
        {
          "finding_id": "rt-001",
          "severity": "blocking",
          "category": "safety",
          "target": "D1 赶海 08:30-10:30",
          "challenge": "干潮 09:12，窗口终点 10:30 已过干潮 1.3 小时，滩涂开始回水",
          "evidence": "Open-Meteo Marine，2026-09-22 取数",
          "action": "窗口收窄为 08:00-10:00，并在方案中标注撤离时刻",
          "status": "resolved"
        }
      ]
    }
  ],
  "verdict": "有条件通过",
  "open_blocking": 0
}
```

字段说明：

- `severity`：`blocking` / `major` / `minor` / `info`
- `status`：`resolved`（已改）/ `accepted_risk`（明知风险接受，需写清理由）/ `open`（未处理）
- `open_blocking` 必须为 0 才能标 `executable_as_of_check`
- 若某轮确实没发现问题，写 `"findings": []`，不要省略整轮

## 六、什么时候可以停

红方复核不是无限循环。满足下面两条就收工：

1. 没有 `open` 状态的 `blocking`
2. 已复核的轮次里，问题数量不再增加（说明边际收益已经耗尽）

一般两轮就够：第一轮挑出真问题，第二轮确认修改没有引入新问题。
第三轮还能源源不断挑出阻塞项，说明方案该重做，而不是继续补。
