# travel-orchestrator · 旅行规划总编排

一个自带**红方复核**的旅行规划 Skill。它做的事不只是把行程排出来，
而是在交付之前，让一个不客气的质疑者把方案过一遍，挑出会让人白跑一趟、
超支、甚至困在滩涂上的地方。

针对观鸟、观星、日出、赶海这类**和时间强绑定**的玩法，它把潮汐、月落、日出
当成硬约束：先锁死这些时刻，再倒推整条动线。这是通用旅行攻略做不到的。

- 零第三方依赖，纯 Python 标准库
- 交付单文件离线 HTML 攻略，双击就开：**能点**（章节跳转 / 折叠 / 返回顶部）、**会动**（观星闪星、赶海海浪、观鸟飞鸟、日出朝霞），也能直接打印
- 所有实时数据走免费接口，不需要注册也不需要 API Key

---

## 为什么做这个

通用的 AI 旅行规划有一个通病：**它不知道潮汐会涨。**

排出来的行程看着合理，上午去哪、下午去哪。但赶海的窗口只有干潮前后一个多小时，
错过就得等下一个潮期；观星撞上满月的话，银河根本看不见；日出点算错半小时，
到了地方太阳已经升完了。

这些不是"体验上的小瑕疵"，是**方案的物理前提**。前提错了，后面排得再漂亮都没用。

所以这个 Skill 的骨架是：

> 先确定不可更改的时刻（潮汐、日出、月落），再往里塞能塞的东西。

## 核心能力

| 能力 | 说明 |
|---|---|
| **需求访谈** | 开场不是问卷，是面试：**一次一屏**（一屏只问同一层的 2-4 个相关子问题，每题给 2-4 个具体选项、推荐项排第一），能自己查到的事实（日出时刻、潮汐、月相、票价、车次）先去查、把数字嵌进问题里再问。五层推进（意图→硬约束→玩法口味→自然观察专项→风险底线），整场 4-5 屏，收尾出「需求共识」等用户确认才动手；含糊答案追一层、追不出就给两个选项，前后矛盾直接顶回去。协议见 `references/intake-interview.md` |
| **红方复核** | 交付前由质疑方逐项挑刺，23 条规则 + 六轮人工质疑清单，阻断项清零才放行。复核属生成过程，**不进交付物**；未解决的风险改写进「踩坑指南」 |
| **反幻觉溯源** | 每个具体数字都要绑定来源与状态，来源超 30 天自动报警，未溯源的不得写成确定值 |
| **自然观察专项** | 观鸟 / 观星 / 日出日落 / 赶海 四项（火烧云评分附在日出卡上）：**嵌在访谈 L3 里问**，先跑可行性核查，再按"条件好 / 条件一般 / 做不到"三档如实告诉用户，做不到的直接给替代，不硬排玩不到的项目 |
| **观鸟** | 近期鸟况、观鸟热点、鸟种识别（BirdNET）、最佳时段（全部免注册） |
| **观星** | 月相与无月暗夜时长、行星可见性、流星雨、波特尔暗光分级 |
| **日出日落** | 精确到分钟，含黄金时刻、蓝调时刻、晨昏蒙影；附太阳轨迹色带与**火烧云指数**（自建评分：云量分层 + 通透度 + 水汽 + 气溶胶，0-3 级） |
| **赶海** | 潮汐极值提取（抛物线插值到分钟级）、赶海窗口计算、涨潮撤离提醒 |
| **常规编排** | 需求澄清、灵感推荐、实时调研、天气研判、行程、美食、预算、待办、踩坑 |
| **动线** | 逐日停靠点清单，名字点开就是高德搜索，编号与 MD 的动线一览一致；配两个跳转：**在高德看全部点位** / **规划整条路线**。页面**不画路线图**（离线单文件里画不出真路径，不如直接跳地图） |
| **预订入口** | 要订的门票/住宿/车票挂上大众点评与美团搜索入口，点进去看当天报价。**不接要 Key 的接口，也不写死房价票价**（写死就会过期） |
| **同源交付** | 一份数据渲染 Markdown 攻略 + 单文件 HTML 攻略；**AI 一层绘制的手绘地图海报**是**可选**的（骨架 + 提示词自动生成） |
| **视觉规范** | B 站配色 × 圆体少女感 × 描边贴纸：9 节固定顺序、六色章节循环、内联 SVG 小图标与小贴图、封面弹幕条与珠光星点、满页闪烁星点、四个专项主题动效。纯 CSS 实现，无脚本无外链 |
| **设计文档** | `references/design-system.md`：设计上下文、色板、排版、图形语言、动效、信息架构、交互、可访问性、打印规则、自检清单 |

## 安装

把整个目录复制到 WorkBuddy 的用户 skill 目录即可：

```bash
# 方式一：用自带的安装脚本
python tools/install.py

# 方式二：手动复制到
#   Windows   %USERPROFILE%\.workbuddy\skills\travel-orchestrator
#   macOS/Linux  ~/.workbuddy/skills/travel-orchestrator
```

装完重启会话生效。**不需要装任何 Python 包**，标准库够用。

## 快速开始

对 WorkBuddy 说一句就行：

> "帮我规划 10 月 1 日到 2 日去威海，两个人，预算 2500，想赶海和观鸟。"

它会先问清几个关键项（出发地、同行人、预算口径、专项偏好），然后：

1. 取实时数据（潮汐、日出、月相、鸟况）
2. 排行程，把赶海窗口和日出时刻先钉死
3. 跑红方复核，挑刺
4. 渲染成 Markdown + HTML 攻略页，给你文件路径（要不要海报、要哪种，可以另外说）

也可以直接用命令行单独跑某个环节：

```bash
# 看威海这两天的潮汐和赶海窗口
python scripts/nature_forecast.py tide --city 威海 --date 2026-10-01

# 日出日落精到分钟
python scripts/nature_forecast.py sun --city 威海 --date 2026-10-01

# 检查接口是不是还活着（对方下线过两次了）
python scripts/nature_forecast.py selftest

# 对一份方案跑红方复核（直接喂方案目录，内部自动合并分片）
python scripts/red_team.py check travel-plan/<trip_id>

# 合并分片 + 结构校验 + 渲染交付物
python scripts/build_trip.py render travel-plan/<trip_id>
```

## 用户故事

### 一、带了望远镜的人

> "国庆去威海，主要想看鸟，顺便赶海。"

一般的攻略会给你"荣成天鹅湖一日游"。
这个会告诉你：10 月是候鸟南迁过境期，滩涂低潮的时候水鸟正好在裸露的滩面上觅食，
所以**赶海和观鸟可以同一时段同一地点一次完成**，不用分两天。

它还会提醒你穿素色衣服、不进保护区禁入滩涂，并给出保护区开放观鸟点的位置。

### 二、要拍星空的人

> "想拍银河，避开光污染。"

排之前它会先查月相。如果那天月亮照度 75%，它会直接说：
**今晚银河基本看不到，建议改拍月面和亮星团，深空目标另择月落后 7 天内的日期。**

它不会为了方案好看而假装那晚适合拍银河。

### 三、带孩子的家长

> "带孩子去赶海，第一次，有点怕。"

这是红方盯得最紧的场景。方案里会出现的是：

- 干潮几点，窗口到几点，**几点必须开始往岸上撤**
- 涨潮从潮沟灌进来的方向，看着还浅其实已经过膝
- 海面风力几级以上取消
- 全场下雨时改去哪

这些不是"温馨提示"，是被当成阻断项检查的。窗口没盖住干潮，方案根本出不来。

## 实际测试案例

仓库的 `examples/weihai-2d/` 里是一份完整的真实案例：北京 → 威海 2 天，2 人，预算 2500，
主要诉求是赶海和观鸟。（该示例在 skill 目录下占 2 层子目录，超过平台「根目录 / 二级目录 / 文件」的限制，
所以只在[源码仓库](https://github.com/fengdihuahua/travel-orchestrator)里；上架包不含它。）

**案例里最有价值的部分不是方案本身，是它被改过的痕迹。**

初稿里有几处当时看不出来的问题，是跑完实测和红方复核才暴露的：

| 初稿写的 | 实测结果 | 处理 |
|---|---|---|
| 干潮 09:12（0.4m） | Open-Meteo Marine 实测 10/1 干潮是 **06:08（-0.71m）**，且数据只覆盖到 07:00 | 干潮 09:12 在任何数据源里都查不到，属凭空写下。窗口整段重排为 04:38-07:38 |
| 赶海排在 08:30-10:30 | 按原窗口出动时潮水已在回涨 | 改为 04:30-07:20，并写明"07:20 开始撤离" |
| 返程"G456 次 15:08 发车"，标为已确认 | 没有任何购票凭证，车次和时刻都未核实 | 改为"车次待定"，购票状态改回待办 |
| 预算分项上限合计 2600 | 超出用户预算 2500 | 住宿压到 350-500，合计正好 2500 |
| 赶海和观鸟分成两天排 | 滩涂低潮时水鸟正在同一片滩面觅食 | 合并到同一时段，省出一个清晨 |

改完之后红方复核结论为**通过（0 阻断 / 0 严重 / 0 提醒）**，渲染产物通过一致性检查。

`tests/run_tests.py` 里有 316 项断言，包含一份故意写坏的对照组，
验证这些规则真的能抓出问题，而不是只在文档里写着。

```bash
python tests/run_tests.py     # 316 项断言，不需要网络
```

## 上架到 SkillHub

开放平台收的是 zip 包（不超过 3MB），包内必须有 `SKILL.md`，且 skill 目录下最多 1 层子目录
（平台原文：只支持「根目录 / 二级目录 / 文件」）。
`SKILL.md` 的 frontmatter 必填项仓库里已经填好，回归测试会盯着不让它们漂：

| 字段 | 说明 |
|---|---|
| `description` | 用途与触发词 |
| `description_zh` / `description_en` | 中英简介，与 `workbuddy.json` 保持同步 |
| `version` | 版本号，与页脚版本标记一致 |
| `author` | 署名，本项目署项目名 `travel-orchestrator`，与 `LICENSE` 著作权人同口径 |
| `category` | 分类（官方字段表标为必填，漏了上传解析会失败） |
| `display_name` / `display_name_en` | 市场展示名 |

打包前自检：

```bash
python tools/pack.py            # 打 zip 到 .workbuddy/dist/，自带 frontmatter、体积、目录层级检查
python tools/verify_all.py      # 编译+测试+红方+渲染+一致性
python tools/install.py         # 同步到 skill 目录（增量，不会删空重装）
```

`tools/pack.py` 会盯住三件平台约束：包内有 `SKILL.md`、体积不超 3 MB、
**结构符合「根目录 / 二级目录 / 文件」**（skill 目录下最多一层子目录）。
包内排除 `tools/`、`tests/`、`examples/`（`examples/weihai-2d/` 在 skill 目录下是 2 层子目录，
超过 1 层上限）、`_shots/` 与 `generated-images/`（截图为 6 MB+ 的 PNG，会把包顶穿 3 MB 上限），
以及 `.gitignore`、`.gitattributes` 这类仓库自用文件。
也可以用官方 `skill-creator` 附带的 `package_skill.py`，但它不做这些检查。

上传入口在客户端【专家·技能·连接器】→【技能】→ 市场右上角【添加技能】，
或开放平台 `open.workbuddy.cn` 的【发布新技能】。**别把调试时的 API Key、
Cookie、个人路径打进包里。**

## 已知限制

诚实写在这里，不藏在文档深处。

1. **潮汐的基准面是 MSL（平均海平面），不是当地潮高基准面。** 数值与官方潮汐表
   可能有系统性偏差。**安全决策（尤其"涨潮前撤离"）必须对照国家海洋信息中心或
   当地潮汐表复核。** 这是这个 Skill 唯一不能替你负责的地方。
2. **潮位数据有效期约 10 天。** 更远日期的数值会返回空，脚本会标 `partial: true`
   并降级提示，不会硬给一个窗口。
3. **朝晚霞评分是自建模型，不是官方预报。** 原来的 Sunset Bot 已于 2026-09 下线，
   现用 Open-Meteo 公开气象数据自建评分。参考可以，别当成承诺。
4. **观鸟数据来自 iNaturalist 公民科学记录**（免注册），说的是"最近有人在哪看到鸟"，
   不等于你到了就一定能看到。方案里标"未核实"的鸟种要出发前再核一遍。
5. **潮汐/日出/月相属天文海洋预报。** 接口返回后仍建议对照官方来源复核。
6. **城市名可能解析到别的省。** 中文重名地名多（大同在山西和黑龙江都有），地理编码取的
   是第一条，错了不会报错，只会让日出日落、月相、霞光整体偏移。脚本 v2.3.0 起会在同名
   候选跨省时打一行 `[注意]`，但时刻敏感的数据**建议直接用经纬度取**。

第一次做旅行类 Skill，这份代码的工程完成度肯定还有打磨空间。
接口失效这类问题需要真实使用才能发现，所以欢迎提 issue。

## 出行安全

潮汐、日出日落、月相、天气等数据都属**预报**性质，存在误差。其中潮位数据以平均海平面
（MSL）为基准，与当地潮高基准面可能有系统性偏差。

**赶海、涉水、登山、夜行等任何涉及人身安全的活动，请务必以官方渠道
（国家海洋信息中心、当地气象与海事部门、景区管理方）发布的实时信息为准。**
本 Skill 产出的方案不能替代专业判断与现场评估。
